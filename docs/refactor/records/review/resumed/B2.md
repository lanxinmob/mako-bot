## 所有权和取消分析

1. workflow.py:41–48 在 guard 内构造新对象并替换槽位。新对象复制全部旧 texts，并继承最早 started_at；incoming 的其他字段和 transport 取最新输入。对象的 version 可以回到 1，但已不承担授权判断。
2. workflow.py:52 仅允许当前槽位中的同一对象出队。旧 sleeper 即使看到相同 version，也不能领取新批次。旧任务持有对象强引用，判断使用 is，不存在对象值相等造成的混淆。
3. workflow.py:55–60 的 finally 只删除自身仍占有的槽位。旧任务被新批次替代后取消，不会删除新批次；最新任务在 debounce 或第二次 guard 等待中取消，会删除全部未出队合并内容，取消继续向调用方传播。
4. 第一次 guard 等待位于 try 外是正确的：此时尚未创建或拥有 batch。标准 asyncio.Lock 获取成功后的临界区及退出不挂起，写入槽位到进入 try 之间没有任务切换/取消注入点。
5. 无 await 清理在当前条件下正确。get/is/pop 为同一事件循环内连续同步操作；两个生产 guard 临界区均无挂起点，任务不能读到后再让其他任务替换槽位。即使 probe 外部持有 guard 并挂起，finally 也不会等待锁而遗留槽位。重复 cancel 不会在这段同步清理中插入第二次异常。
6. workflow.py:54 出队后，所有权转移到该 handle 调用的局部 batch；随后在 64 等待会话锁。此时取消无需再清理 _pending，也不应删除下一批。标准 async with lock 在执行期间取消时释放锁。后续新批次不会重新合并已经出队的输入。

此论证不依赖 GIL，也不承诺跨线程/跨 event-loop 安全。未来若在 guard 临界区增加 await，其他持锁任务可能跨挂起保存旧快照，无锁 finally 的论证需重审；当前代码没有该情况。

## 合并后旧输入的明确语义

旧输入一旦被复制进替代 batch，其处理责任已移交给最新 batch。取消旧 handle 只终止旧等待者，**不是撤回旧文本**；最新批次仍可用最新 transport 发出包含旧文本的合并请求。

取消最新 batch 的拥有者则丢弃整个未出队批次，包括继承的旧文本。旧 sleeper 后续醒来不会恢复它。若取消发生在已出队但等待会话锁时，该局部批次同样丢弃，不回灌 _pending。实际发送开始后的撤销、发送成功后取消与提交一致性不由 B2 保证，不能把本次结论扩展到未来发送接入层。
